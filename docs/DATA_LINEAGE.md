## 2-1. v1.1 변경 사항
E2E 결함을 고치면서 **원본·가정·계산 데이터는 하나도 바꾸지 않았습니다**(`data/raw` 19개 CSV 바이트 동일, 아래 핵심 수치도 그대로입니다). 데이터 관련으로 바뀐 것은 다음 두 가지입니다.
- 자유 메모 입력은 처리 건 유형 `MEMO`로 저장합니다. 그래서 확대 기안 25건 집계(`plans`)에 섞이지 않습니다(D-06).
- 감사 로그는 저장소에 전부 남습니다. 화면·API 스냅샷에는 최근 200건과 전체 건수 `audit_total`만 내려보냅니다.

## 2-2. v1.2 변경 사항
2차 E2E 수정에서도 **원본·가정·계산 데이터와 판단 결과는 바뀌지 않았습니다**(parity 6조건×26건, 골든셋 12건 그대로 통과). 기록을 다루는 방식만 보강했습니다.
- 브라우저 저장 형식이 바뀌면 이전 기록을 `aurora-desk-state.v{번호}`에 보관합니다(삭제하지 않음).
- 한 번만 들어오는 사건(갱신 통보·기안 25건·역제안)은 중복 접수를 거부합니다. 같은 기안이 두 번 집계되는 일이 없습니다. 거부도 감사 로그에 남습니다.
- 휴대폰 화면에서도 근거마다 출처(근거 자료)를 표시합니다. 이 문서의 '원본·계산·가정·모의 구분'이 모든 화면 크기에서 지켜집니다.

## 2-3. v1.3 변경 사항
3차 E2E 수정은 보안·접근성·전송 방식만 바꿨고, **데이터와 판단 결과는 그대로입니다**(parity·골든셋 통과).
- 단일 컨테이너 배포에서 `data/raw` 같은 원본 폴더가 경로 탐색으로 노출되던 문제를 막았습니다. 원본은 판단 엔진만 읽고, 화면에는 계산 결과와 출처 이름만 나갑니다.
- 서버 스냅샷은 gzip으로 압축해 보냅니다. 내용은 그대로이고, 변경 번호가 같으면 같은 내용을 다시 씁니다.
- 시뮬레이션 날짜는 2026-07-01~2027-06-30 범위의 실제 날짜만 받습니다(기준일과 계약 갱신 1년).

## 2-4. v1.4 변경 사항
데이터와 판단 결과는 그대로입니다. 4차 E2E로 **같은 데이터가 어느 경로로 가도 같은 결과가 되는지**를 확인했습니다.
- 브라우저 엔진(localStorage)과 서버(MySQL 호환 DB)에서 같은 시연 여정을 실행한 결과가 처리 건 27개 상태·결재자, 작업, 계약 상태, 발송함까지 모두 같았습니다(E2E M01).
- 아래 §3의 핵심 수치를 문서에서 읽어 시스템 계산값과 대조하는 E2E(V01)를 추가했습니다. 수치를 바꾸면 테스트가 문서 갱신 누락을 잡습니다.
- MySQL 저장소의 목록 순서는 삽입 순번(`seq`)으로 고정했습니다. 같은 밀리초에 여러 건이 기록돼도 감사 로그 순서가 바뀌지 않습니다.

## 2-5. v1.5 변경 사항
데이터와 판단 결과는 그대로입니다.
- **재생성 재현성 확인:** `python scripts/build_dataset.py`를 다시 돌려도 산출물 5개(`dataset.json`, `parity_expected.json`, `data/derived/*.csv` 3개)가 바이트 단위로 같습니다(E2E C02). 이 문서의 '원본 → 계산 → 화면' 경로가 언제든 같은 결과를 냅니다.
- **LLM 설명문의 수치 출처:** 외부 LLM을 켜도 승인자에게 보이는 설명문의 숫자는 사실 목록(위 §3의 계산값)에 있는 숫자뿐입니다. 사실 목록에 없는 숫자가 나오면 그 설명문은 폐기되고, 근거 기반 대체문으로 바뀝니다(E2E L02).

## 2-6. v1.6 변경 사항
데이터와 판단 결과는 그대로입니다.
- **감사 기록의 계보:** 모든 결정·거부·조건 변경·발송은 감사 로그에 남습니다. 이제 처음 기록부터 오래된 순으로 검색해 볼 수 있습니다(`GET /api/audit`, 화면 '전체 기록 보기·검색'). 화면 스냅샷이 최근 200건만 담는 것은 전송 크기 때문이고, 기록 자체는 저장소에 전부 있습니다.
- **채널 입력:** 메신저(MCP)로 들어오는 사건·결정도 화면과 같은 값 목록(사건 종류·역할·행동)만 받습니다. 목록에 없는 값은 저장소에 닿기 전에 거부됩니다.

## 2-7. v1.7 변경 사항
데이터와 판단 결과는 그대로입니다.
- **결정의 출처(누가):** 로그인 모드에서 감사 기록마다 실제 사용자(`user`)가 남습니다. 계보가 '어떤 데이터로 → 어떤 판단 → 어떤 역할이 승인'에서 '… → **누가** 승인'까지 이어집니다. 다른 역할로 결재하려는 시도는 '역할 사칭 거부'로 남습니다.
- **비밀값:** 사용자 비밀번호는 저장소·감사 로그 어디에도 남지 않습니다(메모리 안 PBKDF2 해시만 보관).

## 2-28. v1.28 변경 사항(기능 고정 — 결함 수정만)
데이터와 판단 결과는 그대로입니다.
- **kv 'chain_epochs'(새, '처음부터'에도 유지):** '처음부터' 때마다 그때 체인의 마지막 번호·머리값과, 그 체인에서 밖으로 보낸 머리값 목록(kv 'anchor'의 `sent`, 최근 500개)을 남깁니다(최근 20번). 검증할 때 이 목록에 있는 머리값은 '위조'가 아니라 "'처음부터' 이전에 보낸 머리값" 안내(`notes`)로 나옵니다.
- **kv 'anchor'의 `sent`(새 칸):** 이번 체인에서 밖으로 보낸 머리값 `{id, hash, at}` 목록.
- **감사 기록 `audit.anchor`의 문구:** '→ 메신저로 보냄' → '→ 메신저 전송 요청 — 전달 여부는 외부 채널 전송 목록'(전달 결과는 kv 'deliveries').

## 2-27. v1.27 변경 사항(감사 기록 머리값 · 검색 정렬 규칙)
데이터와 판단 결과는 그대로입니다.
- **kv 'anchor'(새):** 마지막으로 밖에 보낸 머리값 `{at(초), last: {id, hash, at, by, user}, after(보낸 뒤의 머리값)}`. 정기 기록(`AUDIT_ANCHOR_S`)은 명령 잠금 안에서 이 문서를 보고 주기·새 기록 여부를 판단합니다(서버 여러 대도 한 번씩).
- **머리값의 사본(밖):** 메신저 메시지 `[감사 기록 머리값] AU-0042 sha256 <64자 해시>`(outbox·웹훅), 감사 기록 `audit.anchor`(v1.28부터 문구는 '전송 요청'). 이 사본이 DB 밖에 있어야 의미가 있습니다 — 검증은 `GET /api/audit/verify?anchor=AU-0042:<해시>`.
- **감사 검색:** 검색 열 값은 그대로이고, 비교는 질의의 `COLLATE utf8mb4_bin`으로 글자 그대로(v1.25 이전 DB의 unicode_ci 열을 다시 만들지 않음).
- **합성 데이터:** `SEED_CHAIN=1 python e2e/seed_audit.py N` — 감사 기록 N건을 해시 체인까지 이어 붙임(27차 검증 속도 시험).

## 2-26. v1.26 변경 사항(감사 기록 해시 체인 · 요약 평가 행 · 검색 정렬 규칙)
데이터와 판단 결과는 그대로입니다. 감사 기록의 무결성을 확인하는 방법과 요약 평가의 저장 모양이 바뀌었습니다.
- **감사 기록 해시 체인(새 칸):** 기록마다 `prev`(바로 앞 기록의 해시)와 `hash`(id·sim_date·at·topic·actor·case_id·detail·user·prev를 정렬한 JSON의 SHA-256). 머리값은 kv 'seq'의 `audit_head`(번호와 같은 문서·같은 트랜잭션). '처음부터'는 새 체인을 시작합니다(첫 기록 prev=""). v1.25 이전 기록은 해시가 없어 `legacy`로 셉니다. 검증은 `GET /api/audit/verify`(한 시점의 모습에서 오래된 순, 2,000건씩 키셋 페이지).
- **요약 평가: kv 'summary_feedback'(문서 하나) → `feedback` 표:** `id` = `{case_id}|{사람}`(로그인 아이디 또는 역할) · `doc`(case_id·key·rating·note·role·user·at·llm) · `case_id`(생성 열, 색인). 한 사람 한 표는 열쇠로 지켜집니다. 옛 문서는 서버 기동 때, 그리고 구 서버가 다시 쓰면 필요한 순간 옮깁니다.
- **계약 기록의 늦은 이전:** 무중단 배포 중 구 서버가 kv 'renewals'에 쓴 계약도 새 서버가 그 계약을 읽는 순간 행으로 옮깁니다(읽기·지우기는 명령 잠금 안 — 사이에 쓴 것을 잃지 않음).
- **감사 검색 열(`audit.search_text`):** 정렬 규칙이 `utf8mb4_unicode_ci` → `utf8mb4_bin`. 값(소문자로 이어 붙인 화면 표기)은 같고, 비교만 글자 그대로라 'café'는 'cafe'로, 전각 'ａｂｃ'는 'abc'로 찾아지지 않습니다(메모리 저장소·브라우저와 같음).
- **감사 기록 전체 보기:** 전체 건수·찾은 건수·목록을 한 읽기 시점에서(스냅샷과 같은 방식).

## 2-25. v1.25 변경 사항(운영 DB — 정규화 · 감사 기록 보호 · 보기)
데이터와 판단 결과는 그대로입니다. 운영 DB에 저장하는 모양과 지키는 방식이 바뀌었습니다.
- **계약 기록: kv 'renewals'(문서 하나) → `renewals` 표(계약 하나 = 행 하나):** `id`(계약 ID, 예: RC-56AA0B4A) · `doc`(JSON: terms·checks·citations·status·uploaded_on·uploaded_by) · `version` · `status`(doc에서 만든 열, 색인). v1.24의 kv 문서는 v1.25 서버가 처음 뜰 때 행으로 옮기고 지웁니다(`OpsDesk.migrate`, 두 번 해도 같음). 판단 엔진은 판단하는 건이 가리키는 계약 행만 읽습니다(기존: 분석·결재마다 전체). '처음부터'는 이 표도 비웁니다(전과 같음).

- **운영 보기(새, 읽기 전용):** `v_cases`(id·seq·version·state·type·kind·title·target_id·approver·decision·decided_by·received_on) · `v_tasks`(id·case_id·dept·kind·status·title·due·created_on) · `v_audit`(id·seq·sim_date·at_time·topic·actor·user_name·case_id·detail) · `v_renewals`(id·status·counterparty·expiry·auto_renew·annual_fee_krw·currency·notice_deadline·uploaded_on). - **백업:** `mysqldump --single-transaction --routines --triggers`가 표·트리거·보기를 모두 담습니다. 복구한 DB로 서버를 띄우면 번호(kv 'seq')가 이어져 충돌하지 않습니다(25차 AL08).

- **기동 때 이어 쓰기:** 저장소에 '작성 중'으로 남은 건(꺼지기 전 백그라운드 작업)을 기동할 때 이어서 씁니다.
- **사용량 한도:** 429로 끝내 쓰지 못한 건은 `llm`='대체문(openai 사용량 한도)', 판사는 `rule(openai 사용량 한도)`로 남습니다.
