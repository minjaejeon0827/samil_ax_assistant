# 프로젝트 리더 가이드 — 왜 이렇게 만들었고, 어떻게 쓰는가

> 전민재 님이 이 프로젝트를 **직접 설명하고 이어서 개발할 수 있도록**, 프로젝트 리더 관점에서 결정의 이유와 실행 방법을 정리했습니다.

## 1. 핵심 설계 결정 5가지 (면접에서 그대로 말할 수 있게)

**① "AI가 판단한다"가 아니라 "규칙이 판단하고 AI가 설명·검수한다"**
- 이유: 금액·권한·기한은 틀리면 회사가 책임지는 값입니다. LLM이 쓴 숫자가 승인 권한을 바꾸면 안 됩니다.
- 근거: 이전 프로젝트에서 LLM이 쓴 법 조항이 검색 조문과 어긋난 경우가 12.5%(24건 중 3건)였습니다. 그래서 `law`는 코드가 채웠고, 이 원칙을 계산·권한 전체로 넓혔습니다.
- 결과: LLM은 정책 검색 결과를 근거로 설명문을 쓰고, LLM-as-a-Judge가 사실 목록에 없는 숫자를 잡아냅니다(실패 시 재생성 1회). 키가 없어도 같은 판단이 나와 시연과 CI가 재현됩니다.

**② 계약과 기안을 한 엔진, 같은 자로 판단한다**
- 이유: 원본이 경고하는 실패가 "기안만 부결하고 계약을 자동 갱신시키는 것"입니다. 두 결정을 따로 다루면 이 누락이 구조적으로 생깁니다.
- 구현: 기안 판단은 상위 계약 상태를 읽고(`HOLD_STATUSES`), 계약 결정은 연계 기안 상태를 바꿉니다(`_apply_decision_effects`).

**③ covenant 우선 규정을 책임 연쇄의 마지막 고리로 둔다**
- 이유: 정책 원문이 "평시 전결 규정에 우선한다"고 합니다. 금액 규칙 뒤에 덧씌우는 구조가 원문과 같은 모양이고, 판정 경로(trace)가 그대로 결재 근거가 됩니다.

**④ 정보가 없으면 멈춘다**
- 이유: 지급 일정을 가정하면 권한을 잘못 판정할 수 있습니다. 확인 요청 → 회신 → 재판단 흐름이 "정보 부족" 시연 요건과 실무 리스크 관리를 동시에 충족합니다.

**⑤ 브라우저 단독 실행 + 백엔드 parity 테스트**
- 이유: 요구사항 "브라우저에서 바로 실행·새로고침 유지"와 필수 기술 스택(FastAPI·LangGraph·MySQL)을 둘 다 지키려면 같은 규칙을 두 곳에서 돌려야 합니다. 두 구현이 어긋나는 위험은 **6개 조건 × 26건 판단 일치 테스트**로 막았습니다.

## 2. 실행 방법

### 2.1 가장 빠른 방법(브라우저만)
```bash
cd frontend
npm install
npm run dev          # http://localhost:5173
```
새로고침해도 처리 기록이 남습니다(localStorage). 처음부터 다시 하려면 상단 '처음부터'를 누르세요.

### 2.2 전체 스택(FastAPI + LangGraph)
```bash
cd backend
pip install -r requirements-dev.txt
cp ../.env.example ../.env     # API_KEYS 등 설정
uvicorn app.main:app --reload --port 8000
# 다른 터미널
cd frontend
VITE_ENABLE_API=1 VITE_API_URL=http://localhost:8000 VITE_API_KEY=dev-local-key npm run dev
```
상단 '실행 위치'에서 'FastAPI 서버'를 고르면 모든 명령이 서버로 갑니다. 25건 일괄 접수는 202 응답 뒤 job 폴링으로 처리됩니다.

### 2.3 MySQL 멀티유저
```bash
docker compose up --build      # db(MySQL 8.4, schema.sql 자동 적용) + app
```
- 스키마는 MySQL 8.x와 MariaDB 10.6+ 공통 문법입니다(v1.4). 한 명령의 읽기·쓰기는 트랜잭션 하나로 처리되고, 실패하면 전부 되돌립니다.
- DB가 멈추면 API는 503과 '저장소에 연결할 수 없습니다'를 돌려주고, `/api/health`도 503이 됩니다. 로드밸런서 상태 확인에 그대로 쓰세요.

#### 운영 DB 점검·백업·복구 (v1.25, 25차 E2E)
- **연결 재사용**: 서버는 DB 연결을 풀에서 빌려 씁니다(`DB_POOL_SIZE`, 기본 8 — 쉬는 연결을 최대 몇 개 남길지). v1.26부터 빌려줄 때마다 살아 있는지 확인하고(`DB_POOL_PING_S` 기본 0 — DB를 다시 켜도 503 없음), 오류가 난 연결은 버립니다. 한 서버가 동시에 여는 연결은 `DB_POOL_MAX`(기본 10)까지이고, 넘으면 `DB_POOL_WAIT_S`(기본 5초)까지 기다렸다가 그래도 없으면 503 '잠시 뒤 다시'입니다. **서버 수 × `DB_POOL_MAX` + 관리 도구 연결 < MySQL `max_connections`**로 정하세요. `/api/health`의 `db.opened`(지금까지 맺은 연결 수)가 요청 수만큼 늘면 풀이 꺼진 것이고, `db.waited`가 늘면 상한이 좁은 것입니다.
- **계약 기록·요약 평가 표**: 업로드한 계약 기록은 `renewals` 표, 요약 평가는 `feedback` 표(v1.26, (건, 사람) 하나 = 행 하나)에 있습니다. v1.24~v1.25의 kv 'renewals'·'summary_feedback' 문서는 서버가 뜰 때 옮기고 지웁니다. **무중단 배포**로 구 서버와 새 서버가 잠시 함께 돌아도 괜찮습니다 — 구 서버가 kv에 다시 쓰면 새 서버가 그 기록이 필요한 순간 옮깁니다(v1.26).
- **머리값 기록·화면 검증(v1.27)**: 감사 로그의 '체인 검증' 버튼(서버 모드)으로 감사 담당이 직접 검증합니다. `AUDIT_ANCHOR_S`(예: 3600)를 켜면 그 주기마다 머리값(마지막 기록 id·전체 해시)을 메신저로 보냅니다(서버가 여러 대여도 주기마다 한 번, 새 기록이 없으면 안 보냄). 그룹 CEO는 `POST /api/audit/anchor`로 바로 보낼 수 있습니다. 의심되면 메신저에 남은 머리값으로 `GET /api/audit/verify?anchor=AU-0042:<해시>` — 체인을 통째로 다시 계산한 위조도 '밖에 적어 둔 머리값과 다름'으로 짚습니다. 메신저 채널은 DB 계정과 다른 사람이 관리해야 의미가 있습니다. 감사 기록에는 '→ 메신저 전송 요청'으로 남고 실제 전달 여부는 '외부 채널 전송' 목록에서 확인합니다(실패하면 다시 보내기). '처음부터' 이전에 받은 머리값으로 검증하면 '위조'가 아니라 "'처음부터'(시각) 이전에 보낸 머리값"이라는 안내(`notes`)가 나옵니다 — 메신저 메시지 시각이 그 '처음부터'보다 앞서는지 확인하세요(v1.28). 머리값은 메신저 메시지의 `AU-0042:<64자 해시>`를 그대로 넣어야 하며, 형식이 다르면 422입니다.
- **감사 기록 위변조 탐지(v1.26)**: 감사 기록마다 바로 앞 기록의 해시(`prev`)와 자기 해시(`hash`)가 있습니다. `GET /api/audit/verify`가 고친 기록('내용이 바뀜')·지운 자리('바로 앞 기록이 바뀌거나 지워짐')·끝 잘림을 짚습니다. 응답의 `head`(마지막 해시)를 하루 한 번 메신저나 WORM 저장소에 적어 두면, 체인 전체를 다시 계산한 위조도 드러납니다. v1.25 이전 기록은 `legacy`로 세고 건너뜁니다.
- **감사 기록 보호**: `audit` 표는 트리거(`audit_no_update`·`audit_no_delete`)가 UPDATE·DELETE를 거부합니다. '처음부터'(그룹 CEO)만 같은 연결에서 `@aurora_reset=1`을 켜고 지우며, 지운 건수를 새 감사 기록으로 남깁니다. 트리거·보기는 `schema.sql`에도 있고, 이미 만든 DB는 서버가 뜰 때 없으면 만듭니다. **MySQL 8에서 바이너리 로그가 켜져 있으면 트리거를 만들 때 SUPER 또는 `log_bin_trust_function_creators=1`이 필요할 수 있습니다** — 만들지 못하면 서버는 그대로 뜨고 `/api/health`의 `db.guards`가 False이니, 관리자 계정으로 `schema.sql`을 적용하세요. 한계: 앱 계정 비밀번호를 가진 사람은 `@aurora_reset`을 직접 켤 수 있습니다. 위변조를 막아야 하는 감사라면 감사 기록을 다른 계정·보관소로 복제하세요.
- **사람이 SQL로 볼 때**: 보기 `v_cases`(id·유형·상태·결재자·결정)·`v_tasks`(처리 건·부서·상태·기한)·`v_audit`·`v_renewals`(상대방·만료·연간 금액·상태)를 쓰세요. 보기는 `SQL SECURITY INVOKER`라 조회하는 사람의 권한으로 돕니다. 읽기 전용 계정 예: `CREATE USER 'aurora_ro'@'%' IDENTIFIED BY '…'; GRANT SELECT ON aurora_desk.v_cases TO 'aurora_ro'@'%';`(보기마다, 그리고 보기가 읽는 표의 SELECT 권한도 필요).
- **백업**: 쓰기를 막지 않는 방식으로 — `mysqldump --single-transaction --routines --triggers aurora_desk > backup.sql`(MariaDB는 `mariadb-dump`). `--triggers`를 빼면 복구한 DB에 감사 기록 보호가 없습니다. 25차 AL08에서 쓰기가 계속되는 중에 백업(21~28ms)·복구하고 그 DB로 서버를 띄워 이어서 접수·결재·검색했습니다(번호 충돌 0).
- **복구**: `CREATE DATABASE aurora_restore CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;` → `mysql aurora_restore < backup.sql` → 앱 계정에 권한(`GRANT ALL ON aurora_restore.* TO 'aurora'@'…'`) → `MYSQL_DB=aurora_restore`로 서버 시작. 검색은 v1.27부터 질의에서 `COLLATE utf8mb4_bin`으로 글자 그대로 비교하므로, v1.25 이전 DB의 검색 열(unicode_ci)을 다시 만들지 않습니다 — v1.26은 기동 때 표를 복사해 고치느라 무중단 배포 중 옛 서버의 쓰기를 2.8초 멈췄습니다(감사 12만 건). **스키마를 바꿀 때는 '구 서버가 쓰는 중에 이 ALTER가 표를 잠그는가'를 먼저 확인하세요.** 명령줄로 한글을 넣거나 볼 때는 `--default-character-set=utf8mb4`를 붙이세요(빼면 저장값이 깨져 보이거나 깨진 값이 들어갑니다 — 25차에서 시험 도구가 실제로 이 실수를 했습니다).

### 2.4-1 E2E 테스트 (v1.1)
```bash
cd frontend && npm install && cd ..
pip install -r backend/requirements-dev.txt mcp
bash e2e/run_all.sh          # 브라우저 26 + API·MCP 18 + 풀스택 7 + 2차 18 + 3차 17 + 4차 13 + 5차 10 + 6차 11 + 7차 8 + 8차 9 + 9차 9 + 10차 8 + 11차 7 + 12차 6 + 13차 3 + 14차 4 + 15차 6 + 16차 5 + 17차 5 + 18차 5 + 19차 5 + 20차 5 + 21차 9 + 22차 8 + 23차 8 + 24차 9 + 25차 9 + 26차 9 + 27차 9 + 28차 9 + 30차 11 + 32차 10 = 296개, 약 28분
```
- 사용하는 도구: Playwright 1.63.0(frontend 개발 의존성 — `cd frontend && npm ci`로 함께 설치)과 Node 내장 `node:test`. 브라우저가 없다면 `cd frontend && npx playwright install chromium`을 한 번 실행합니다. 외부 LLM E2E(5차)는 `requirements-dev.txt`의 `langchain-openai`를 씁니다.
- MariaDB가 없으면 4차의 운영 DB 테스트 7개는 '건너뜀'으로 표시되고 나머지는 그대로 실행됩니다. CI처럼 반드시 DB까지 검증하려면 `REQUIRE_DB=1 bash e2e/run_all.sh`.
- 결과: `e2e/reports/{ui,api,fullstack,round2,round3,round4,round5,round6,round7,round8,round9,round10,round11,round12,round13,round14,round15}.json`(통과 여부와 측정값), 같은 이름의 `.txt`(로그)
- 2차 E2E(`round2`)는 여러 탭, 두 결재자 동시 결정, 서버 끄기·켜기, 저장 형식 변경, 키보드·모바일, MCP 오류 경로를 다룹니다. 서버를 실제로 껐다 켜므로 8000·4173·4174 포트가 비어 있어야 합니다.
- 3차 E2E(`round3`)는 Dockerfile과 같은 빌드(`dist-docker`)를 FastAPI가 서빙하는 구성(8010 포트)에서 경로 탐색·보안 헤더·우회 지시·날짜 검증, 시간대, 저사양 CPU, 320px, 오프라인, 접근성(axe-core), 동시 30명, 느린 4G를 시험합니다.
- 4차 E2E(`round4`)는 MySQL 호환 DB(MariaDB)를 테스트가 직접 띄워(3307 포트, `e2e/.mariadb`) 전체 여정·모드 간 결과와 안내 일치·DB 장애·감사 로그 순서를 시험하고, 문서·영상의 수치와 테스트 수가 실제와 같은지 대조합니다. MariaDB가 없으면 `sudo apt-get install -y mariadb-server`(Ubuntu)로 설치합니다. 문서를 고치면 `round4`가 숫자 불일치를 잡아 줍니다.
- 5차 E2E(`round5`)는 모의 OpenAI 호환 서버(8900 포트)를 띄워 외부 LLM 경로(정상·환각·오류·무응답·지연), 새 환경에서 E2E 도구 찾기, 데이터 재생성 재현성, 결재 서류 인쇄를 시험합니다.
- 6차 E2E(`round6`)는 같은 모의 서버의 Anthropic 경로, 원격 MCP 토큰·입력 검증, 감사 로그 전체 열람, 메모 500건 누적, 날짜 한계 일관성을 시험합니다.
- 7차 E2E(`round7`)는 로그인 모드 서버(8000, 토큰 2초짜리 8002)로 역할 사칭·무단 조회·잠금·만료·위조 토큰·화면 로그인·MCP 계정·대화상자 포커스를 시험합니다.
- 8차 E2E(`round8`)는 로그인 모드에서 쓰기 기능 전부 × 역할 6개 권한 매트릭스, 부서 작업 완료, 로그아웃 무효화, 로그인 실패 감사, 잠금 악용(127.0.0.2에서 공격), MCP 재로그인, 역할 변경, 사용자 200명 기동, 로그인+MySQL+단일 컨테이너 조합을 시험합니다. **새 쓰기 기능을 만들면 `permissions.py`에 역할을 넣고 P01의 `allowed` 표에도 추가하세요.**
- 9차 E2E(`round9`)는 합성 데이터(`e2e/seed_audit.py`)로 감사 기록 1만~5만 건이 쌓인 서버와 브라우저를 만들어 순서·속도·저장을 보고, 60MB 요청, 활동 중 로그인 연장, 감사 행위자, 프록시 뒤 접속 주소를 시험합니다. **계속 늘어나는 기록(감사·발송함)을 화면에 쓸 때는 `repo.list()`로 전부 읽지 말고 `tail`·`count`·`search`를 쓰세요.**

### 2.5 실제 LLM 사용
```bash
pip install langchain-openai      # 또는 langchain-anthropic
export LLM_PROVIDER=openai OPENAI_API_KEY=...   # 판단 결과는 그대로, 설명문·Judge만 LLM으로 바뀜
pip install ragas datasets && python -m eval.run_eval   # 공식 RAGAS 지표 추가 계산
```
외부 LLM을 켤 때 알아 둘 동작(v1.5, 5차 E2E로 검증):
- **환각 차단:** 판사 점수는 규칙 판사(사실 목록 숫자 대조)와 LLM 판사 중 더 엄격한 쪽을 씁니다. 다시 써도 통과하지 못한 LLM 설명문은 폐기하고 근거 기반 대체문을 보여 줍니다. 결재 서류에 '설명문 작성: …'으로 누가 썼는지 표시됩니다.
- **장애 대응:** `LLM_TIMEOUT_S`(기본 8초) 안에 답이 없거나 오류가 나면 재시도 1회 후 대체문으로 진행합니다. 판단·결재는 멈추지 않습니다. 한 번 실패하면 `LLM_COOLDOWN_S`(기본 60초) 동안 LLM을 부르지 않습니다(회로 차단). '처음부터'를 누르면 바로 풀립니다.
- **속도:** 여러 건은 `LLM_CONCURRENCY`(기본 16)만큼 동시에 분석합니다. 판사를 통과한 설명문은 입력이 같으면 재사용합니다. 호출당 0.5초일 때 기안 25건은 2.1초 걸립니다(이전 25초).
- **사용량 한도(v1.17):** 429는 장애가 아닙니다. `Retry-After`만큼 기다렸다 다시 부르고(최대 `LLM_RATE_WAIT_S`=30초), 그래도 안 되면 그 건만 대체문입니다(차단기는 열지 않음). 제공자의 동시 요청 한도를 알면 `LLM_MAX_INFLIGHT`를 그 값으로 두세요. 동시 4건 한도에서 기안 25건은 약 6초입니다.
- **분당 토큰 한도(v1.22):** 제공자에 분당 토큰 한도(TPM)가 있으면 `LLM_TPM`(예: 30000)을 그 값보다 조금 낮게 두세요. 서버가 보낼 메시지의 토큰을 어림해(글자 ÷ 2 × 1.1) 한도를 넘기 전에 기다리므로 429를 받지 않습니다(시험: 3초당 2.4만 토큰에서 25건 429 0회, 10초). 창 길이는 `LLM_TPM_WINDOW_S`(기본 60). 서버가 여러 대면 `LLM_TPM_SCOPE=shared`(v1.23, MySQL)로 저장소에서 함께 세게 하세요(23차: 서버 2대 429 104회 → 0회). 기본값 server는 서버마다 따로 셉니다.
- **한도를 모를 때(v1.24):** `LLM_TPM`을 비워 두면 OpenAI가 응답마다 보내는 남은 토큰 헤더(`x-ratelimit-remaining-tokens`·`reset-tokens`)를 보고 속도를 맞춥니다(24차: 429 37회 → 0~1회). 헤더를 주지 않는 제공자(현재 Anthropic 경로)는 기다리지 않고 429 재시도만 합니다. 끄려면 `LLM_TPM_HEADERS=0`.
- **계약서 요약(v1.22):** LLM을 켜면 업로드한 계약서에 'LLM 요약'이 붙습니다. 값·판단은 계속 규칙이 정하고, 요약에 추출값에 없는 숫자가 있으면 버리고 근거 기반 요약을 씁니다.
- **기다리지 않는 판단(v1.16):** 규칙 판단·결재란은 LLM을 기다리지 않고 먼저 저장됩니다. 처리 건 화면에는 'LLM이 설명문을 쓰는 중'과 사실 목록의 숫자로 만든 설명이 보이고, 이때 결재해도 됩니다. LLM 설명은 잠금 밖에서 만들어 판단·입력 문구가 그대로일 때만 바꿔 넣습니다. 접수 작업 '완료'는 설명까지 끝난 시점입니다. 결재·문구 반영·조건 변경이 다시 분석한 건의 설명은 응답 0.4초 뒤(`ENRICH_DEBOUNCE_S`, 연달아 바꾼 조건은 마지막 것만) 백그라운드에서 만들어집니다. 서버가 꺼지면 다음 기동 때 이어 쓰고, 정상 종료 때는 최대 `SHUTDOWN_DRAIN_S`(8초) 기다려 마칩니다(v1.17).
- **사내 게이트웨이:** OpenAI 호환 서버면 `OPENAI_BASE_URL`만 바꾸면 됩니다. 5차 E2E는 이 방식으로 모의 서버(`e2e/mock_llm.py`)에 붙여 정상·환각·오류·무응답·지연을 시험합니다.

### 2.6 MCP 서버를 Claude Desktop에 등록
`claude_desktop_config.json`:
```json
{
  "mcpServers": {
    "aurora-desk": {
      "command": "python",
      "args": ["-m", "app.mcp_server"],
      "cwd": "C:/axwar/aurora-campaign-desk/backend",
      "env": { "DESK_API_URL": "http://localhost:8000", "DESK_API_KEY": "dev-local-key" }
    }
  }
}
```
MCP를 로그인 모드 서버에 붙일 때는 `DESK_USER`·`DESK_PASSWORD`(그 MCP가 대신할 사람의 계정)를 함께 넣습니다. MCP는 그 계정의 역할로만 결재합니다.

원격(사내 메신저 봇 등): `MCP_TRANSPORT=streamable-http MCP_HOST=0.0.0.0 MCP_PORT=8765 MCP_TOKEN=<긴 무작위 값> python -m app.mcp_server` → 주소 `http://<서버>:8765/mcp`, 모든 요청에 `Authorization: Bearer <MCP_TOKEN>` 헤더가 필요합니다. 외부 주소로 열 때 `MCP_TOKEN`이 없으면 시작하지 않습니다(v1.6 — 이전에는 누구나 접속해 그룹 CEO로 승인할 수 있었음). FastAPI(8000)와 포트가 겹치지 않습니다. 외부에 열 때는 리버스 프록시에서 HTTPS도 붙이세요.
- 도구에 잘못된 값(행동·역할·사건 종류·회신 종류·건 ID)을 넣으면 API를 부르지 않고 '허용 값'을 한국어로 안내합니다.

대화 예시: "그룹 CEO 승인 대기 보여줘" → `list_pending_approvals("GROUP_CEO")` → "CS-0001 승인해, 의견은 조건변경 통보" → `submit_decision`. 권한이 없으면 서버가 거부합니다.

## 3. AXHub 배포 (Claude Code에 보낼 문장)
1. 대회 프로젝트 루트(README.md와 `.claude` 폴더가 있는 곳)에 이 저장소 내용을 복사합니다. `.claude`·`.codex`·`.agents`는 건드리지 않습니다.
2. 커밋 전에 기록 키가 제외되는지 확인합니다.
   ```bash
   git check-ignore .claude/settings.local.json .codex/hooks.json .agents/hooks.json
   ```
3. Claude Code에 이 문장을 보냅니다.
   > 이 폴더의 Dockerfile로 axhub에 배포해 줘. 테넌트는 lounge, 이미 만든 앱 samil-ax-assistant에 이어서 배포해 줘. 환경변수 API_KEYS=demo-public-key, ALLOWED_ORIGINS=https://samil-ax-assistant-kqzw.axhub.app, AUTH_MODE=jwt, JWT_SECRET=<32자 이상 무작위 값>, USERS=<아이디:비밀번호:역할;…> 로 설정해 줘. 저장소 없이 올리는 방식(axhub up)은 쓰지 마.
   - `AUTH_MODE=jwt`는 공개 배포에서 필수입니다. 이 값이 없으면 API 키(화면 코드에 들어 있음)만으로 누구나 그룹 CEO로 결재할 수 있습니다(7차 E2E J-01). 역할은 `MARKETING_TEAM·MASIL_CEO·GROUP_CEO·FINANCE·SCM·CONTRACT_OWNER` 중 하나입니다.
   - 심사용 시연 계정이 필요하면 역할별로 하나씩 만들고 비밀번호는 제출 화면에만 적습니다(저장소에 넣지 않음).
4. 실패하면 "다시 배포해 줘"를 2~3회 보내고, 그래도 안 되면 소스 zip으로 제출합니다(AXHub는 선택 사항).

> 참고: 브라우저 엔진이 기본이라 서버가 잠들어도 화면은 동작합니다. 서버 모드로 바꾸면 로그인 창이 뜨고, 로그인한 계정의 역할로만 결재합니다(§6).

### 3.1 배포 확인(읽기 전용 스크립트 `e2e/smoke_remote.cjs`)
배포한 주소에서만 생기는 문제(흰 화면·자산 경로·원본 파일 노출·보안 헤더·CORS·옛 버전 이미지 등)를 확인합니다. **서버에는 GET·HEAD·OPTIONS만 보내고**, 접수·결재·'처음부터' 같은 쓰기 요청은 보내지 않습니다(실행 끝에 보낸 요청 수를 보여 줌). 설치할 것이 없고 Node 18 이상이면 됩니다. 파일 하나만 복사해 어느 폴더에서나 돌릴 수 있습니다.
```bash
node e2e/smoke_remote.cjs https://<배포 주소>/                          # 정적·서버 배포를 스스로 판별
node e2e/smoke_remote.cjs https://<배포 주소>/ --api-key demo-public-key  # 서버 배포: 스냅샷·감사·체인 검증까지(읽기만)
node e2e/smoke_remote.cjs https://<배포 주소>/ --browser                  # 실제 브라우저(PC·휴대폰 폭) — 먼저 npm i -D playwright@1.63.0 && npx playwright install chromium
```
- 판정: ✅ 통과 · ⚠️ 확인 권장(호스트 설정에 따라 괜찮을 수 있음) · ❌ 실패(고쳐야 함) · ℹ️ 참고. 실패가 있으면 종료 코드 1, 결과는 `smoke_report.json`과 화면 캡처(`smoke_1440.png`·`smoke_390.png`)로 남습니다.
- `--browser`를 정적 배포에 쓰면 상황 1 접수 → 새로고침 유지를 실제로 눌러 봅니다. 그 브라우저의 저장소에만 쓰이고 서버로 가는 요청은 없으며, 끝나면 지웁니다. 서버 배포에서는 아무것도 누르지 않습니다.
- 자주 나오는 실패와 고치는 법: **P05 자산 404**(하위 경로 배포인데 자산이 `/assets/…`) → `vite.config.ts`에 `base: "./"` 넣고 다시 빌드 · **P03 빌드 전 원본 배포**(`/src/main.tsx`를 직접 부름) → `npm run build`의 `dist`를 배포 · **X01 원본·설정 파일 노출** → `static_output_dir`가 `dist`인지 · **B01 React 19** → `package.json`을 시험한 버전(18.3.1)으로 · **A07 인증 없는 조회 200** → `API_KEYS`·`AUTH_MODE` 확인 · **A08 CORS** → `ALLOWED_ORIGINS`를 화면 주소로.
- 이 작업 공간에서 정적(루트·하위 경로 + 절대/상대 자산)·서버 배포와 일부러 망가뜨린 배포(원본 폴더 배포·주소 오류)로 판정을 확인했습니다. 서버 배포 확인 전후로 처리 건·감사 기록 수가 그대로였습니다.
- **v1.29(30차)에서 더한 확인:** **A14 계약서 PDF 읽기 준비** — `/api/health`의 `contracts`로 업로드 없이 확인(29차 AP-01: 배포 이미지에 pypdf가 없어 PDF 업로드가 모두 422) · **U04 로그인 창 예시 글자** — 로그인 모드 서버에서 `--browser`일 때 이 브라우저의 화면 설정만 '서버'로 바꿔 로그인 창을 띄우고 아이디·비밀번호 칸의 예시 글자를 읽기만 함(29차 AP-02: 예시 글자에 그룹 CEO 아이디·공용 비밀번호). 실패하면 아이디는 앞 3글자만, 비밀번호는 값 없이 '있음'만 적습니다.
- **v1.30(32차)에서 더한 확인:** **B05 번들의 역할 이름표** — 화면 번들의 역할 이름표에 권한표 밖 역할(예: 31차 AR-02의 `TEST_AURORA`)이 있으면 실패. 기대 버전 기본값은 `1.30.0`(`--expect-version`으로 바꿈).

### 3.2 32차 수정본(v1.30) 다시 배포하기 — 31차 결함을 배포 주소에 반영
31차는 다시 배포한 주소(`https://samil-ax-assistant-kqzw.axhub.app`, v1.29.0)에서 29차 결함 11건이 반영된 것을 확인했지만, 로그인 창 예시 글자(test.aurora·**7개 계정의 공용 비밀번호**)가 다시 생겼고(AR-01) 권한표에 없는 TEST_AURORA 계정이 있었습니다(AR-02). 둘 다 **이 소스에는 없는 것**이라, 배포가 이번에도 다르게 고친 사본에서 빌드된 것으로 봅니다. 32차가 나머지 결함(AR-03~AR-06)을 소스에서 고쳤고, 배포 주소에는 **다시 배포해야** 반영됩니다.
1. **모든 계정의 비밀번호를 바꿉니다.** 31차에 공용 비밀번호가 공개 화면에 노출됐으므로, 다시 배포하기 전에 바꿔야 합니다. 계정마다 다른 비밀번호(10자 이상, 영문·숫자·기호 중 두 종류 이상, 아이디를 넣지 않음)를 정하고 `cd backend && python -m app.api.auth hash`로 만든 해시를 `USERS=ceo.kang:<해시>:GROUP_CEO;contract.park:<해시>:CONTRACT_OWNER;…`처럼 넣습니다. 비밀번호는 제출 화면에만 적고 문서·화면·채팅에는 적지 않습니다.
2. **test.aurora를 `USERS`에서 뺍니다.** 역할은 권한표의 6개(GROUP_CEO·MASIL_CEO·CONTRACT_OWNER·MARKETING_TEAM·FINANCE·SCM)만 씁니다. 권한표에 없는 역할이 있으면 이 소스의 서버는 기동을 거부합니다(`USERS의 역할이 올바르지 않습니다`).
3. **소스를 이 zip으로 맞춥니다.** 사본을 고쳐 쓰지 말고 이 zip을 그대로 씁니다. 로그인 칸 예시 글자나 TEST_AURORA 이름표가 남아 있으면 `npm run build`·Docker 빌드가 `check-bundle: 실패`로 멈춥니다(§3.1).
4. **Dockerfile로 다시 배포**합니다(§3의 문장 그대로). 빌드 단계가 PDF 모듈·글자 인식 도구와 화면 번들을 확인합니다.
5. **확인:** `node e2e/smoke_remote.cjs https://samil-ax-assistant-kqzw.axhub.app --expect-version 1.30.0 --browser` → 실패 0, A14·U04·B05 ✅. 그다음 실제 Chrome으로 31차 실패 케이스를 봅니다 — 로그인 창(AR01), 스캔 계약서 업로드가 '통보 기한 미확인'·계약 담당 내부 확인 작업인지(AR04), 기한 경과 뒤 '기한 전' 통보 작업이 '취소'인지(AR10·AR11).
6. 메모리 저장소라 다시 배포하면 31차 시험 기록(감사 262건)은 사라집니다. 시연 전 그룹 CEO로 '처음부터'를 한 번 누르면 깨끗하게 시작합니다.

## 5. 실전 프로젝트에 바로 적용하는 방법
| 실무 단계 | 이 프로젝트에서 가져갈 것 |
|---|---|
| 요구사항 | 정책 문서의 수치를 `policy_rules.json` 같은 **단일 규칙 소스**로 옮기고 출처를 함께 남긴다 |
| 설계 | 결정 패키지 스키마(proposal·recommendation·evidence(kind/scale/source)·alternatives·authority·needs_info·on_approve/on_reject)를 먼저 합의한다 |
| 구현 | 계산·권한은 결정적 코드로, LLM은 설명·검수·검색으로 역할을 나눈다 |
| 검증 | 계약 테스트(반환 규격) → 도메인 수치 고정 → 시나리오 → 평가 게이트(정확도가 1차 지표, RAGAS는 보조) → **사용자 여정 E2E**(v1.0은 단위 테스트를 모두 통과했지만 E2E에서 결함 11건이 나왔습니다. 결정 뒤의 연결부는 E2E로만 잡힙니다) |
| 운영 | 감사 로그·기한 감시·낙관적 잠금·출력 마스킹을 처음부터 넣는다 |
| 변경 | 조건 변경 = 미결 건 재검증 + 기승인 권한 상향 시 무효화 + 후속 작업 취소. 단, 사람이 건 보류(확인 요청)는 재검증 대상에서 빼기 |
| 성능 | 측정부터 합니다(E2E가 클릭 → 화면 반영, LCP·CLS, 저장 횟수를 기록). v1.1에서는 명령 단위 일괄 저장(쓰기 595 → 9회), 서버 기동 시 인덱스 미리 적재, 글꼴 굵기 정리를 했습니다. v1.2에서는 자동 갱신을 '변경 번호만 확인, 바뀌면 스냅샷' 방식으로 만들어 대기 중 통신을 10초에 112바이트로 줄였습니다 |
| 연동 | 외부 시스템은 느리고, 실패하고, 같은 요청을 두 번 보냅니다. 21차에서 전자결재가 3초 걸려도 결재 응답은 5ms였습니다(커밋 뒤 별도 스레드). 일시 장애는 재시도로, 중복 콜백은 event_id로, 위조는 서명과 시각 창으로 막습니다. 연동의 판단·권한 검사는 화면과 같은 명령을 그대로 씁니다 |
| 입력 | 사용자가 쓰는 중인 글은 화면의 어떤 갱신에도 지워지면 안 됩니다. 20차에서 AI 설명이 도착하자 승인자가 쓰던 결정 의견이 지워졌습니다. 서류를 '판 번호'로 새로 그렸기 때문입니다 |
| 수명 | 새로 만든 칸은 언젠가 지워져야 합니다. 19차에서 18차에 넣은 '결재 뒤 도착한 AI 설명' 칸이 재상신된 새 결재 서류에 그대로 붙어 있었습니다. 새 칸을 넣을 때 '다시 분석하면 어떻게 되는가'까지 정합니다 |
| 서류 | 결재 서류는 결재한 순간의 모습으로 남아야 합니다. 18차에서 AI 설명이 '작성 중'일 때 결재하자, 결재 뒤 도착한 LLM 설명이 서류의 설명을 조용히 바꿨습니다. 결재자가 본 적 없는 글이 서류에 남은 것입니다. 결재 뒤의 정보는 따로 보관하고 감사 기록을 남깁니다 |
| 순서 | 늦게 끝나는 작업은 순서를 보장하지 않습니다. 17차에서 조건을 90일 → 45일 → 보수로 바꾸자, 먼저 시작한 45일 분석이 먼저 끝나 결재 서류 14건에 '승인자: Masil 대표'(실제는 그룹 CEO)를 적었습니다. 판단 '라벨'이 같아서 통과했습니다. 작업마다 표를 주고, 결과를 넣을 때 표를 확인합니다 |

## 7. 한계와 정직하게 말할 것
- 다음 단계(v1.21·v1.22)의 SSO(로그아웃 포함)·전자결재·메신저는 표준을 따르는 모의 서버로만 시험했습니다. 실제 사내 시스템에 붙일 때 IdP 클레임 이름·전자결재 양식을 맞추고 같은 E2E(`round21`·`round22`)를 그 환경에서 다시 돌리세요.
- PRD §14 리스크 표의 행마다 그것을 지키는 테스트가 있습니다(22차 AI01·23차 AJ01). 리스크를 새로 적으면 `e2e/risk_guards.cjs`에 짝이 되는 테스트도 적으세요. §15 표의 '검증' 열 테스트와 '남은 일'도 23차가 대조합니다. 그래야 표가 '약속'이 아니라 '확인된 사실'로 남습니다.
- LLM은 기본 오프라인 모드입니다. 설명문은 템플릿이지만 판단은 동일합니다.
- MySQL 저장소는 MySQL 호환 DB(MariaDB 10.11)로 E2E를 돌렸습니다. MySQL 8.4 자체는 이 환경에서 받을 수 없어 시험하지 못했습니다(스키마는 두 DB 공통 문법). v1.25의 트리거는 MySQL 8에서 바이너리 로그 설정에 따라 권한이 더 필요할 수 있습니다(§2.3).
- 감사 기록 보호 트리거는 앱이 실수로 고치거나 지우는 것을 막습니다. 앱 계정 비밀번호를 가진 사람의 의도적인 우회는 막지 못하지만, v1.26의 해시 체인 검증이 고친 자리·지운 자리를 찾아냅니다. 체인 전체를 다시 계산한 위조는 v1.27의 머리값 메신저 기록으로 드러납니다 — 단, 메신저(밖)까지 같은 사람이 고칠 수 있으면 막지 못합니다(WORM 저장소 기록은 다음 단계).
- 느린 4G(1.6Mbps)에서 글꼴 전체 적재는 3.8초입니다. 본문은 1.3초에 보이고 화면 밀림이 0.021이라 그대로 두었습니다.
- RAGAS는 공식 패키지 대신 같은 정의의 로컬 지표로 계산했습니다(키가 있으면 공식 지표 추가).
- 광고 카피·외부 회신은 합성·모의입니다(화면에 배지로 표시).
- 리드타임 단축 효과는 추정입니다.
- **29차는 배포 주소를 사람이 쓰는 Chrome으로 시험했고, 1~28차가 놓친 결함 12건이 나왔습니다**(작업 공간에만 깔린 PDF 모듈, 로그인 창의 계정 예시 글자, 결재권자가 아닌 사람의 확인 요청 등). 30차가 모두 재현해 고쳤고, 31차에 다시 배포한 주소에서 11건이 반영된 것을 확인했습니다. 다만 로그인 창 예시 글자는 다른 사본에서 다시 생겨(31차 AR-01), 32차부터는 그런 번들이면 빌드가 멈춥니다(§3.1·§3.2). 면접에서는 '단위·E2E를 다 통과해도 배포 환경에서만 생기는 결함이 있었고, 그래서 깨끗한 의존성 환경과 배포 확인 스크립트를 시험에 넣었다'고 말하면 됩니다.
- 스캔 PDF의 글자 인식은 흐린 스캔에서 숫자를 틀립니다(30차: '60일' → 'CO'). 그때는 값을 지어내지 않고 '확인 필요'로 멈춰 사람이 넣게 합니다.
